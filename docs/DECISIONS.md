# Decisions

Where the build spec was ambiguous, the more secure option was chosen and recorded here.
Each entry: context → decision → consequence. Newest last.

## D-001 Naming

The product/repo is **veilauth**. Spec identifiers stay as written: crypto labels `zk2fa/v1/...`,
npm scope `@zk2fa/*`, Android package `app.zk2fa`. Changing a crypto label would change every
derived key, so it can only happen with a new `v2` spec.

## D-002 HKDF salt is empty

The spec gives HKDF with `info` only. The IKM (`masterKey`, `recoveryKey`) is already uniformly
random, so the salt adds nothing; we fix it to the empty string (= 32 zero bytes, RFC 5869 §2.2)
so every platform computes the same thing. Pinned by the RFC 5869 A.3 vector.

## D-003 Envelope version byte is authenticated

GCM AAD = `version ‖ UTF8(ctx)`, not just `ctx`. A future `v2` envelope can never be
re-labelled as `v1` (or vice versa) without failing authentication.

## D-004 Strict base64url

No padding, no whitespace, no standard-alphabet characters, canonical trailing bits. One
ciphertext has exactly one encoding, which keeps test vectors byte-identical and removes a
malleability surface.

## D-005 KDF parameter policy on the client

`prelogin` is answered by the server, so a malicious server could send `m=8 KiB, t=1` to make
offline cracking cheap. Clients refuse anything outside `65536 ≤ m ≤ 262144 KiB`,
`3 ≤ t ≤ 16`, `p = 1`, `alg = argon2id` and a 16-byte salt, and never fall back. `p` is fixed to
1 because libsodium's `crypto_pwhash` (Android) only supports one lane. Upper bounds stop a
server from DoS-ing phones with a 4 GiB KDF.

## D-006 Canonical JSON = RFC 8785 (JCS) subset

"Canonical JSON" is implemented as JCS restricted to objects, arrays, strings, booleans, null
and safe integers. Floats and lone surrogates are rejected. This is what makes
encrypt-with-fixed-nonce vectors byte-identical between JS, Kotlin and Python.

## D-007 Padding format

`u32be(len) ‖ json ‖ zeros` up to a multiple of 256. Decoders verify the length and that all
padding bytes are zero. The 8 KB blob limit is read as 8192 base64url characters, giving at
most 5888 padded bytes (23 buckets).

## D-008 Token plaintext additions

- Added `trashedAt` (int | null) so the 30-day trash is encrypted client state. The server only
  ever sees hard deletes (tombstones).
- All keys are always present, so the canonical form is stable.
- Unknown keys are preserved on round-trip, so an older client never strips a field added by a
  newer one.
- String limits are counted in UTF-16 code units, the native length in both JS and Kotlin.

## D-009 AAD hardening

Every id in an AAD must be a lowercase canonical UUIDv7 and `kind` comes from a closed enum,
so `|` cannot be injected to forge another context. Additional contexts:
`zk2fa/v1/rvk|{userId}` for the recovery-wrapped vault key (separate from `vk`) and
`zk2fa/v1/device|{userId}|{deviceId}` for encrypted device names.

## D-010 Recovery words: BIP39 as an encoding only

24 BIP39 English words encode the 32-byte recovery key plus an 8-bit SHA-256 checksum. The
BIP39 seed function (PBKDF2-SHA512 "mnemonic") is not used. The checksum is always verified.
The wordlist is pinned in `spec/bip39-english.txt` by its SHA-256.

## D-011 E-mail normalisation

`toLowerCase(NFKC(trim(email)))`, used for storage and the fake-salt HMAC, so
`Alice@Example.com` and the full-width `ＡＬＩＣＥ@example.com` cannot become two accounts or
leak existence through different fake salts.

## D-012 Server auth hash

PBKDF2-HMAC-SHA256 with 100 000 iterations (the Workers PBKDF2 ceiling) and a 16-byte per-user
salt, rotated on every password change. Comparison is constant time. The real brute-force cost
is the client-side Argon2id. The same construction is used for `recoveryAuth`.

## D-013 otpauth:// parsing rules

- `digits` 6–8 (Steam is always 5), `period` 1–86400 s, secret 1–128 bytes of strict base32
  (spaces, hyphens, lower case and `=` padding are normalised first). MD5 is rejected.
- HOTP without `counter` is rejected (the Key URI format requires it).
- Steam is detected by `otpauth://steam/…`, `encoder=steam`, issuer "Steam" (any case), or
  `steam://SECRET`. Steam always uses SHA1/30 s/5 characters.
- The `issuer` parameter wins over the label prefix.
- Error messages carry a stable code and never echo the input, because the input contains the
  secret.

## D-014 Google Authenticator migration

Per-entry problems (MD5, an unknown type) are reported per entry and never abort the whole
batch. Multi-QR batches can be scanned in any order. Mixing two exports is an error. Input is
capped at 64 KiB.

## D-015 Independent reference implementation for vectors

`spec/test-vectors.json` is generated by `scripts/gen_test_vectors.py`, which uses Python
`cryptography` (OpenSSL) and shares no code with the TS or Kotlin clients. CI regenerates it and
fails on drift. The Python script also asserts published KATs: the Argon2 reference vector,
RFC 5869 A.3, RFC 4226 Appendix D, RFC 6238 Appendix B and the BIP39 "legal winner" vector.
Steam has no official vectors, so its vectors are cross-checked between the independent Python
and TS implementations.

## D-016 Fixed nonces are test-only

Fixed-nonce helpers live only in `@zk2fa/crypto/testing`. ESLint forbids importing it from any
`src/` file, and production `seal()` has no nonce parameter.

## D-017 Vault key never leaves WebCrypto on the web

`kek` and `recoveryKek` are derived with `HKDF → deriveKey` straight into non-extractable
`CryptoKey`s, and the vault key is unwrapped with `subtle.unwrapKey`, so neither exists as raw
bytes in JS memory. Only password change and recovery ask for an extractable vault key, briefly,
to re-wrap it.

## D-018 Web client auto-update (PWA)

Requirement (Sina): the JS web client updates itself the way a website does, without anyone
reinstalling. Design:

- The Worker serves the web app; a `vite-plugin-pwa` service worker checks for a new build on
  start, on focus and every 60 minutes.
- If the vault is **locked**, the new version activates immediately (reload).
- If the vault is **unlocked**, the new version is downloaded in the background and activates on
  the next lock or reload. A non-blocking "Update ready, reload" banner offers to apply it now.
  The page never reloads silently while unlocked, because a reload locks the vault.
- Every build publishes its asset hashes (SRI and release notes), so anyone can compare what
  they are served against the reproducible build.

This keeps the known limit from the threat model: whoever controls the server can ship new JS.
High-risk users should use the Android app.

## D-019 Android updates: signed APKs only, no remote code

Loading code from the network (DexClassLoader, downloaded JS in a WebView) is not done in the
Android app. It would let a compromised server or GitHub account run arbitrary code inside the
vault, and Google Play forbids it. Instead:

- **GitHub flavor:** an in-app updater checks the GitHub Releases API for a newer `versionCode`,
  downloads the APK over HTTPS and verifies its SHA-256 against the release manifest. Before
  installing it uses `PackageManager.getPackageArchiveInfo` to check that the APK's signing
  certificate digest equals the pinned release certificate. Installation uses a `PackageInstaller`
  session. On Android 12+, when veilauth is the installer of record,
  `setRequireUserAction(USER_ACTION_NOT_REQUIRED)` applies the update without a prompt; otherwise
  the user confirms once. Android itself also refuses an update signed with a different key.
- **Play flavor:** Google Play In-App Updates API (flexible update).
- **F-Droid flavor:** no updater. F-Droid handles updates.

## D-020 Automated builds and releases

- Every PR and push to `main`: format, lint, typecheck, tests, vector drift check, dependency
  audit, CodeQL, secret scan (Phase 0, `.github/workflows/ci.yml`).
- Push to `main`: deploy Worker and web app to staging (added in Phase 1).
- Tag `v*`: production deploy, signed APK + AAB built in GitHub Actions with the keystore from
  repository secrets, a `SHA256SUMS` file and a release manifest attached to a GitHub Release
  (added in Phase 1 for the web build and Phase 3 for Android). The in-app updater (D-019) reads
  that release.
