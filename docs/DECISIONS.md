# Decisions

Where the build spec was ambiguous, the more secure option was chosen and recorded here.
Each entry: context → decision → consequence. Newest last.

## D-001 Naming

The product/repo is **veilauth**. Spec identifiers stay as written: crypto labels `zk2fa/v1/...`,
npm scope `@zk2fa/*`, Android package `app.zk2fa`. Changing a crypto label would change every
derived key, so it can only happen with a new `v2` spec.

## D-002 HKDF salt is empty

The spec gives HKDF with `info` only. The IKM (`masterKey`, `recoveryKey`) is already uniformly
random, so the salt adds nothing; we fix it to the empty string (= 32 zero bytes, RFC 5869 §2.2)
so every platform computes the same thing. Pinned by the RFC 5869 A.3 vector.

## D-003 Envelope version byte is authenticated

GCM AAD = `version ‖ UTF8(ctx)`, not just `ctx`. A future `v2` envelope can never be
re-labelled as `v1` (or vice versa) without failing authentication.

## D-004 Strict base64url

No padding, no whitespace, no standard-alphabet characters, canonical trailing bits. One
ciphertext has exactly one encoding, which keeps test vectors byte-identical and removes a
malleability surface.

## D-005 KDF parameter policy on the client

`prelogin` is answered by the server, so a malicious server could send `m=8 KiB, t=1` to make
offline cracking cheap. Clients refuse anything outside `65536 ≤ m ≤ 262144 KiB`,
`3 ≤ t ≤ 16`, `p = 1`, `alg = argon2id` and a 16-byte salt, and never fall back. `p` is fixed to
1 because libsodium's `crypto_pwhash` (Android) only supports one lane. Upper bounds stop a
server from DoS-ing phones with a 4 GiB KDF.

## D-006 Canonical JSON = RFC 8785 (JCS) subset

"Canonical JSON" is implemented as JCS restricted to objects, arrays, strings, booleans, null
and safe integers. Floats and lone surrogates are rejected. This is what makes
encrypt-with-fixed-nonce vectors byte-identical between JS, Kotlin and Python.

## D-007 Padding format

`u32be(len) ‖ json ‖ zeros` up to a multiple of 256. Decoders verify the length and that all
padding bytes are zero. The 8 KB blob limit is read as 8192 base64url characters, giving at
most 5888 padded bytes (23 buckets).

## D-008 Token plaintext additions

- Added `trashedAt` (int | null) so the 30-day trash is encrypted client state. The server only
  ever sees hard deletes (tombstones).
- All keys are always present, so the canonical form is stable.
- Unknown keys are preserved on round-trip, so an older client never strips a field added by a
  newer one.
- String limits are counted in UTF-16 code units, the native length in both JS and Kotlin.

## D-009 AAD hardening

Every id in an AAD must be a lowercase canonical UUIDv7 and `kind` comes from a closed enum,
so `|` cannot be injected to forge another context. Additional contexts:
`zk2fa/v1/rvk|{userId}` for the recovery-wrapped vault key (separate from `vk`) and
`zk2fa/v1/device|{userId}|{deviceId}` for encrypted device names.

## D-010 Recovery words: BIP39 as an encoding only

24 BIP39 English words encode the 32-byte recovery key plus an 8-bit SHA-256 checksum. The
BIP39 seed function (PBKDF2-SHA512 "mnemonic") is not used. The checksum is always verified.
The wordlist is pinned in `spec/bip39-english.txt` by its SHA-256.

## D-011 E-mail normalisation

`toLowerCase(NFKC(trim(email)))`, used for storage and the fake-salt HMAC, so
`Alice@Example.com` and the full-width `ＡＬＩＣＥ@example.com` cannot become two accounts or
leak existence through different fake salts.

## D-012 Server auth hash

PBKDF2-HMAC-SHA256 with 100 000 iterations (the Workers PBKDF2 ceiling) and a 16-byte per-user
salt, rotated on every password change. Comparison is constant time. The real brute-force cost
is the client-side Argon2id. The same construction is used for `recoveryAuth`.

## D-013 otpauth:// parsing rules

- `digits` 6–8 (Steam is always 5), `period` 1–86400 s, secret 1–128 bytes of strict base32
  (spaces, hyphens, lower case and `=` padding are normalised first). MD5 is rejected.
- HOTP without `counter` is rejected (the Key URI format requires it).
- Steam is detected by `otpauth://steam/…`, `encoder=steam`, issuer "Steam" (any case), or
  `steam://SECRET`. Steam always uses SHA1/30 s/5 characters.
- The `issuer` parameter wins over the label prefix.
- Error messages carry a stable code and never echo the input, because the input contains the
  secret.

## D-014 Google Authenticator migration

Per-entry problems (MD5, an unknown type) are reported per entry and never abort the whole
batch. Multi-QR batches can be scanned in any order. Mixing two exports is an error. Input is
capped at 64 KiB.

## D-015 Independent reference implementation for vectors

`spec/test-vectors.json` is generated by `scripts/gen_test_vectors.py`, which uses Python
`cryptography` (OpenSSL) and shares no code with the TS or Kotlin clients. CI regenerates it and
fails on drift. The Python script also asserts published KATs: the Argon2 reference vector,
RFC 5869 A.3, RFC 4226 Appendix D, RFC 6238 Appendix B and the BIP39 "legal winner" vector.
Steam has no official vectors, so its vectors are cross-checked between the independent Python
and TS implementations.

## D-016 Fixed nonces are test-only

Fixed-nonce helpers live only in `@zk2fa/crypto/testing`. ESLint forbids importing it from any
`src/` file, and production `seal()` has no nonce parameter.

## D-017 Vault key never leaves WebCrypto on the web

`kek` and `recoveryKek` are derived with `HKDF → deriveKey` straight into non-extractable
`CryptoKey`s, and the vault key is unwrapped with `subtle.unwrapKey`, so neither exists as raw
bytes in JS memory. Only password change and recovery ask for an extractable vault key, briefly,
to re-wrap it.

## D-018 Web client auto-update (PWA)

Requirement (Sina): the JS web client updates itself the way a website does, without anyone
reinstalling. Design:

- The Worker serves the web app; a `vite-plugin-pwa` service worker checks for a new build on
  start, on focus and every 60 minutes.
- If the vault is **locked**, the new version activates immediately (reload).
- If the vault is **unlocked**, the new version is downloaded in the background and activates on
  the next lock or reload. A non-blocking "Update ready, reload" banner offers to apply it now.
  The page never reloads silently while unlocked, because a reload locks the vault.
- Every build publishes its asset hashes (SRI and release notes), so anyone can compare what
  they are served against the reproducible build.

This keeps the known limit from the threat model: whoever controls the server can ship new JS.
High-risk users should use the Android app.

## D-019 Android updates: signed APKs only, no remote code

Loading code from the network (DexClassLoader, downloaded JS in a WebView) is not done in the
Android app. It would let a compromised server or GitHub account run arbitrary code inside the
vault, and Google Play forbids it. Instead:

- **GitHub flavor:** an in-app updater checks the GitHub Releases API for a newer `versionCode`,
  downloads the APK over HTTPS and verifies its SHA-256 against the release manifest. Before
  installing it uses `PackageManager.getPackageArchiveInfo` to check that the APK's signing
  certificate digest equals the pinned release certificate. Installation uses a `PackageInstaller`
  session. On Android 12+, when veilauth is the installer of record,
  `setRequireUserAction(USER_ACTION_NOT_REQUIRED)` applies the update without a prompt; otherwise
  the user confirms once. Android itself also refuses an update signed with a different key.
- **Play flavor:** Google Play In-App Updates API (flexible update).
- **F-Droid flavor:** no updater. F-Droid handles updates.

## D-020 Automated builds and releases

- Every PR and push to `main`: format, lint, typecheck, tests, vector drift check, dependency
  audit, CodeQL, secret scan (Phase 0, `.github/workflows/ci.yml`).
- Push to `main`: Cloudflare Workers Builds deploys the Worker and web app to production
  (D-050; until then GitHub Actions deployed to staging).
- Tag `v*`: signed APK + AAB built in GitHub Actions with the keystore from
  repository secrets, a `SHA256SUMS` file and a release manifest attached to a GitHub Release
  (added in Phase 1 for the web build and Phase 3 for Android). The in-app updater (D-019) reads
  that release.

## D-021 Clients choose `userId` and `deviceId`

The AAD of the wrapped vault key and of encrypted device names contains these ids, so the client
needs them before anything is uploaded. Clients generate UUIDv7s. The server validates the format
and rejects ids that are already taken (`ID_TAKEN`). A device id that belongs to another account
can never be re-used.

## D-022 Sync push concurrency

All writes of a push run in one `db.batch()` transaction. Its first statement sets
`vault_revision = CASE WHEN vault_revision = <read value> THEN <read value + 1> ELSE NULL END`.
If another push committed in between, the `NOT NULL` constraint aborts the whole batch, so two
pushes can never share a revision and no client can miss changes. The Worker retries up to 5
times with jittered backoff, then answers `409 SYNC_RETRY`, and clients simply sync again.

## D-023 Sessions are checked on every request

Besides verifying the JWT, every authenticated request checks that the device row is not revoked
and that the token's `stamp` matches `users.security_stamp`. Logout, device revocation, password
change and recovery therefore take effect immediately instead of after the 15-minute token
lifetime. It costs one indexed D1 read per request.

## D-024 Failed-login policy

- Rate Limiting binding: 5 requests per minute per (IP, e-mail) for prelogin, login and recovery.
- Lockout per **(e-mail, IP)**: after 5 failures within 24 h, the pair is locked for
  1 min · 2^(n−5), capped at 1 h. Locking per pair instead of per account stops an attacker from
  locking a victim out from another IP.
- Per e-mail from any IP: 3 failures within 1 h make Turnstile mandatory on the next attempts.
- Counter keys use HMAC'd e-mails and IPs, and unknown e-mails go through the identical path
  (including a dummy PBKDF2), so neither the counters nor timing reveal whether an account exists.

## D-025 Registration limit in D1

The Workers Rate Limiting binding only supports 10 s and 60 s windows, so "3 registrations per
hour per IP" is a fixed-window counter in D1. Turnstile, when configured, is also required for
registration (optional since D-049).

## D-026 Recovery is two calls and the recovery key is single-use

`POST /auth/recover/start` proves the recovery key (`recoveryAuth`) and returns `userId` and the
recovery-wrapped vault key, which the client needs to unwrap the vault key and build the new AAD.
`POST /auth/recover` repeats the proof and atomically replaces the password hash, both wraps and
the recovery hash. It also rotates the security stamp, which revokes all sessions. A new recovery
key is always issued, so the old words stop working.

## D-027 Registration reveals an existing e-mail

`register` answers `EMAIL_TAKEN` for an existing e-mail. Hiding this would require mandatory
e-mail verification before an account exists, which the spec makes optional. The leak is
limited by 3 registrations per hour per IP plus Turnstile. Prelogin and login do not leak.

## D-028 Server-side envelope checks

The server cannot decrypt anything, but it rejects item blobs that are not strict base64url,
not envelope version 1, or not padded to a 256-byte bucket. A buggy or old client therefore
cannot leak exact item sizes.

## D-029 Tombstone purge horizon

When the daily cron purges tombstones older than 90 days, it records the highest purged revision
per user in `users.tombstone_horizon`. A `GET /sync?since=` below that horizon returns
`full: true` with the complete item list, and the client replaces its cache.

## D-030 Tooling substitutions

- `@cloudflare/vitest-pool-workers` was renamed to `@cloudflare/vitest-plugin` (same project,
  Vitest 4). Worker tests use it with a local D1 and the real migrations.
- `spec/api.openapi.yaml` is generated with Zod 4's native `z.toJSONSchema` (JSON Schema 2020-12
  is OpenAPI 3.1's schema dialect). `zod-to-openapi` hit a CJS/ESM dual-package problem with
  Zod 4. CI fails if the file drifts from the schemas.

## D-031 Minimal EdDSA JWT

Access tokens are built and checked with WebCrypto Ed25519 directly. The verifier accepts only
the exact header `{"alg":"EdDSA","typ":"JWT"}` that the service issues. There is no algorithm
negotiation, so `alg: none` and HS/RS confusion attacks are impossible.

## D-032 Refresh-token storage

The current refresh token's SHA-256 is stored on the device row (one device = one session =
one refresh family) with `refresh_expires_at`. Rotated hashes move to `refresh_history` until
they would have expired. Presenting one again revokes the family (`REFRESH_REUSED`). Rotation is
a conditional update on the old hash, so two concurrent refreshes cannot both win.

## D-033 Turnstile per environment

Development: off when `TURNSTILE_SITE_KEY` is empty. Staging: Cloudflare's always-pass test
keys, so E2E tests can register. Production: real keys. A missing secret outside development is
a hard error, never a silent bypass. **Amended by D-049:** production may run without Turnstile. Staging was removed by D-050.

## D-034 Logging allowlist

The Worker logs only through `logError(event, { name, path })`: error class names and route
patterns. ESLint forbids `console` everywhere else.

## D-035 CSP allows `'wasm-unsafe-eval'`

Argon2id runs in WebAssembly (hash-wasm, spec §4.4), and browsers only compile WebAssembly when
the CSP allows `'wasm-unsafe-eval'`. That keyword permits WebAssembly compilation only: `eval`,
`new Function` and string timers stay blocked. Everything else matches the spec's policy
(`default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'`). Zod's
`new Function` feature probe is switched off (`jitless`) before any schema loads, so the
console shows no violations (the E2E test asserts this).

## D-036 Turnstile runs in its own same-origin frame

Turnstile needs a script from `challenges.cloudflare.com`. Instead of adding that origin to the
app's CSP, the widget lives in `/turnstile` (a static page with its own CSP that allows only
Cloudflare's challenge origin, and only frameable by us). It hands the token to the app with
`postMessage`; the app checks the message's origin and source frame. The vault page never loads
third-party code, and the widget is only shown on sign-up and on log-in after
`TURNSTILE_REQUIRED`.

## D-037 Native `<dialog>` instead of Radix UI

Radix Dialog's scroll lock injects a `<style>` element at runtime, which `style-src 'self'`
blocks. The more secure option is to keep the strict CSP and use the native `<dialog>` element,
which gives focus trapping, Escape-to-close and the modal backdrop without injected styles.
Tailwind is used as specified.

## D-038 Web session storage

IndexedDB holds only what the server holds: item ids, revisions, envelopes, the wrapped vault
key and the KDF parameters, plus the refresh token and pending (encrypted) local changes. The
vault key exists only inside the crypto Web Worker as a non-extractable `CryptoKey`; reloading
or closing the tab locks the vault (spec §6 default). Unlock works offline from the cached wrap;
if that fails it falls back to an online log-in (password changed elsewhere). Refreshes are
serialised across tabs with the Web Locks API and always use the latest stored refresh token, so
two tabs can never present a rotated token (which would revoke the session family, D-032). When
the server ends a session, the encrypted cache and unsynced edits are kept for the same user's
next log-in and wiped if a different account logs in. "Stay unlocked on this device" is not
offered yet (Phase 5 with passkey PRF).

## D-039 Conflict resolution details

Push conflicts (spec §5.3) are resolved without ever dropping a token:

- token edited on both sides: the server copy stays, the local version is saved as a new token
  whose account name ends in " (conflicted copy)";
- HOTP with the same secret on both sides: one token with the higher counter;
- local delete vs remote edit: the edit wins (the token survives);
- local edit vs remote delete: the local edit is pushed again on top of the tombstone;
- folders and settings: the server copy wins;
- identical content: the local change is dropped.

## D-040 Trusted Types default policy

The CSP sets `require-trusted-types-for 'script'; trusted-types default`. The only policy is
`default`, and it accepts same-origin script URLs (the crypto worker, the service worker,
lazy chunks) and rejects every HTML or script string. The app never uses `innerHTML`; the
service worker is generated with the Workbox runtime inlined so it needs no `importScripts`.

## D-041 Subresource Integrity and published hashes

A build plugin adds `integrity="sha384-…"` to every script and stylesheet tag in `index.html`
after minification, and the post-build script verifies those hashes and writes `SHA256SUMS` for
every published file. Browsers cannot apply SRI to `new Worker()` or to lazily imported chunks,
so those are covered by `SHA256SUMS`, which each GitHub Release prints in its notes.

## D-042 Master password strength

Sign-up and password change require at least 10 characters and a zxcvbn score of 3 or more
(zxcvbn-ts, loaded only on those screens), with the e-mail as a user input to penalise.

## D-043 Device names are not sent yet

`device.nameEnc` is optional in the API. The web client sends `null` for now: a name encrypted
with the vault key cannot be produced at log-in time (the vault key is unwrapped after the
server answers), and naming devices is a Phase 4 settings feature.

## D-044 Phase 2 scope

Phase 2 ships what spec §8.3 lists for the web MVP (sign-up with recovery key, log-in, unlock,
vault CRUD, QR/URI/manual add, sync, auto-lock) plus the pieces the §8.1 E2E needs or that cost
little on top of the existing API: trash, password change, device list/revoke and account
deletion. Importers, encrypted export, folders, icons, reordering and the recovery flow UI stay
in Phase 4 as planned. The web auto-lock offers 30 s / 1 / 5 / 15 min; "never" is
Android-with-biometric only (spec §2).

## D-045 Android crypto library: BouncyCastle

spec/crypto.md §1 names libsodium/argon2kt for Argon2id and Tink for HKDF on Android. The Kotlin
core (`apps/android/core/crypto`) uses BouncyCastle's lightweight API for both
(`Argon2BytesGenerator`, `HKDFBytesGenerator`) instead. The primitives are unchanged; only the
library differs. Reasons: it is pure JVM, so the exact code that ships in the app is the code
that runs `spec/test-vectors.json` on every CI run (no native library that only exists on a
device); one well-reviewed dependency replaces two; and Tink's JVM and Android artifacts would
otherwise need swapping per build. AES-GCM, HMAC and SHA-256 stay on `javax.crypto` /
`java.security`. Cost: pure-JVM Argon2id with 64 MiB is slower than native code, roughly 1–3 s
on a mid-range phone, which only happens at log-in and password unlock.

## D-046 Android module layout

Everything that can run on a plain JVM lives in Gradle modules without the Android plugin, so it
is built and tested anywhere: `:core:otp`, `:core:crypto` (both checked against
`spec/test-vectors.json`), `:core:api` (models generated from `spec/api.openapi.yaml` by
`packages/shared/scripts/gen-kotlin.mjs`, with a CI drift check, plus the OkHttp client) and
`:core:vault` (log-in, unlock, offline store semantics, sync and conflict rules, ported from the
web client and tested against a fake server). `:app` holds only Android glue: Room, Keystore,
biometrics, camera, WorkManager, UI and the updater. `-Pveilauth.coreOnly=true` builds the core
modules without Google Maven.

## D-047 Android certificate pinning

The app pins the API host with OkHttp's `CertificatePinner` to the SPKI hashes of the root CAs
Cloudflare issues edge certificates from (Google Trust Services R1/R3/R4, ISRG X1/X2, SSL.com
RSA/ECC and the 2022 roots, USERTrust RSA/ECC for Sectigo). Pinning the leaf or intermediate
would break the app whenever Cloudflare rotates its certificate, which happens every few weeks;
roots cover rotation and a change between Cloudflare's CAs, and still stop a rogue certificate
from any other CA in the system store. `network_security_config.xml` also disables cleartext and
user-installed CAs. Self-hosters on another CA override the list with `-Pveilauth.certPins`
(SELF_HOSTING.md, "Android releases"). The GitHub download client for the updater is not pinned: every APK
is checked by SHA-256 and signing certificate instead (D-019).

## D-048 Android Phase 3 scope

- Log-in, password and biometric unlock, vault list, add (camera, screenshot via the Photo
  Picker, Google Authenticator export, `otpauth://` link, manual), edit, trash, sync, auto-lock,
  settings and the updater. Sign-up, recovery, password change, devices and account deletion
  stay in the web app until Phase 4 (the log-in screen says so).
- Turnstile: the server asks for it on log-in only after three failed attempts for an account.
  The app has no WebView, so it shows a message (log in once on the web, or wait an hour) rather
  than embedding Cloudflare's script. Revisit in Phase 4.
- Flavors: `github` (in-app updater) and `fdroid` (none). A `play` flavor with Google Play
  In-App Updates comes with a Play listing.
- Biometric unlock wraps the vault key under an Android Keystore AES-GCM key that requires a
  strong biometric for every use and is invalidated by a new enrollment; the app then falls back
  to the password and turns biometric unlock off. "Never auto-lock" is offered only with
  biometric unlock on (spec §2).
- Refresh tokens are sealed with a separate Keystore key (no user authentication) so the
  background sync worker can run while the vault is locked; it moves ciphertext only.
- `versionCode = major·1 000 000 + minor·1 000 + patch`, taken from the tag.
- QR decoding uses ML Kit's bundled model (on-device, no Play Services). It is not free software,
  so the F-Droid build will need a ZXing-based scanner before submission (Phase 5).

## D-049 Turnstile is optional in production

Sina chose to run production without Turnstile for now. An empty `TURNSTILE_SITE_KEY` turns it
off in every environment, not only development; `/config` then returns no site key, the web app
shows no widget, and sign-up and the log-in escalation after three failures skip the check.
Sign-up stays limited to 3 accounts per hour per IP (D-025) and log-in by the Rate Limiting
binding plus the per-account lockout (D-024), so automated sign-ups are slowed, not blocked.
Setting a site key turns Turnstile back on; a site key without a secret is still a hard error
(D-033). The release workflow fills the site key only when both GitHub settings are present.

## D-050 One production environment, deployed by Cloudflare from Git

Sina dropped staging to keep the setup simple. `wrangler.jsonc` now describes a single Worker,
`veilauth`, with one D1 database; `wrangler dev` and the tests use the same file with a local,
simulated D1. Sina creates the Worker in the Cloudflare dashboard and connects it to the GitHub
repository (Workers Builds), so every push to `main` builds and deploys, with D1 migrations
applied automatically (D-051). The GitHub Actions deploy jobs, the staging
workflow, the `ENVIRONMENT` variable and the D1 setup script are gone. GitHub Actions still runs
CI on every push, and a `v*` tag still builds the signed Android app and the GitHub Release.
The web app keeps being served by the Worker (same origin, no CORS), so no Pages project is
needed. The trade-off: changes reach production without a staging check, so CI (unit, Worker
and E2E tests) is the only gate before users see them.

## D-051 The Worker migrates its own database

Sina asked for tables to be created on first run and upgraded automatically. `pnpm build` (and
`pnpm run deploy`) bundles `migrations/*.sql` into `src/db/migrations.gen.ts`; CI fails if that
file is stale, and a test checks it lists exactly the files in `migrations/`. On the first
request each isolate handles (and before the daily cron), `ensureSchema` applies every pending
migration in file order, each as one D1 batch (one transaction) together with its row in
`d1_migrations`, the same table `wrangler d1 migrations apply` uses, so both ways agree. If two
isolates race, the loser sees the migration recorded and carries on. Cost: one small query per
isolate start. Migrations stay forward-only and must be safe to run against live data, since
there is no separate migration step before the new code serves traffic.
